# Physical RTX 5060 on NexusOS

Target confirmed on the host: GeForce RTX 5060, PCI `10de:2d05`. The requested
implementation runs on the NexusOS kernel and its Linux userspace compatibility
layer. A Linux VM, CPU renderer or QEMU's emulated display does not satisfy the
physical GPU requirement.

## Implemented

`kernel/nexus-kernel/src/drivers/nvidia.rs` participates in native boot discovery.
It identifies NVIDIA display functions, checks enabled memory decoding and the
PCI power state, maps one page of the RTX 5060's firmware-assigned BAR0 and reads
`NV_PMC_BOOT_0` and `NV_PMC_BOOT_42`. It checks the two architecture fields agree
with the published GB200 Blackwell value, then logs chip and revision numbers.
This path never resets engines, enables bus mastering or starts firmware.

The native bootstrap path now selects one detected card and reads pinned
production GB202/GB206 files from `BIN/NVFW` on a FAT32 disk or USB medium.
`shared/nexus-nvidia` checks the RISC-V descriptor version/regions, ELF firmware
section names, sizes, overlaps and CRCs, then checks both full-file SHA256 values
against the pinned 615.78.08 release. These containers are firmware, never CPU
executables. Malformed or modified material is refused before DMA allocation.

The kernel allocates two physically contiguous, aligned, zero-filled buddy
blocks and copies the real RISC-V and FMC images. FMC hash, signature and public
key material stays intact for future hardware authentication. All buffers are
CPU-owned and **unpublished**: there is no active device DMA or GPU virtual
address mapping yet. Failed second allocations roll back the first block;
Drop clears and frees owned memory. These preparations do not boot GSP.

The matching full GSP-RM container and external microcode are now available
with `-WithGspFirmware`. A bounded Python 3.14 reader downloads NVIDIA's
615.78.08 package, checks its pinned size and published SHA256, skips the
embedded shell script/Linux decompressor, and extracts only firmware and its
license. Neither the installer nor any bundled executable runs on the host.

Native loading streams the 27,043,992-byte RM container and 58,215,936-byte
microcode into owned physical pages; it does not put them in the 16 MiB heap.
Both input and copied bytes must match pinned full-file hashes. The RM ELF's
version, section bounds, names and overlaps are checked; the GB20x signature
stays intact in its own 4096-byte buffer. The microcode header/fingerprint
must match this release. The unaligned RM image is copied into separate padded
pages, with every copied chunk read back and compared.

The driver generates NVIDIA's three-level radix format, follows every stored
root/middle/leaf entry back to its original frame and checks unused bytes and
tail padding. Partial allocations and checksum refusals reclaim all owned
frames. These are **CPU physical addresses, unpublished to the device**;
device DMA/IOMMU activation, authenticated WPR layout, signature verification and
the actual GSP boot/RPC transport remain to be implemented.

The GB206 initial boot ABI now has native owned buffers: 256-byte WPR metadata,
256-byte FMC arguments, the packed 860-byte version-2 FSP chain-of-trust request,
184-byte RM arguments and a 4 KiB Libos region list. The request preserves the
real FMC hash/key/signature and RM signature. Firmware-owned VRAM positions and
the authenticated `verified` word remain zero. The WPR boot manifest field uses
the descriptor's `manifestOffset`, separately from its monitor manifest.

The release profile uses seven logs (five 64 KiB and two 4 KiB), a 1 MiB FRTS
buffer and two 256 KiB RPC queues. The shared PTE page contains 129 physical
page addresses, including itself. Only the CPU command header is initialized;
the remote status queue stays zero until GSP actually owns it. Each log has
its physical address in the second 64-bit word. These pages are mapped into
the unpublished AMD-Vi domain with read-only firmware/arguments and read/write
FRTS, WPR metadata, queues and logs. All backing allocations remain owned with
the bootstrap, including on construction or mapping failure.

For the standard 8 GiB GB206 profile, the requested heap is 137 MiB, PMU
reservation is `0x19a0000` and FRTS is requested `0x19c0000` bytes from the end
of VRAM. These are source-derived requests, not measured VRAM layout. ICU and
CBC-SR scrub flags follow the pinned GB206 HAL's false values. FSP transport,
secure boot, reset/ownership and physical acceptance are still missing.

The 860-byte COT request is also staged as its actual 868-byte single-packet
MCTP/NVDM wire representation. The no-std FSP transport primitive follows the
GB206 HAL's GH100 EMEM channel: it checks command and response queues are empty,
writes zero-padded DWORDs, verifies EMEM auto-increment and publishes TAIL before
the interrupt-triggering HEAD. Receive checks inclusive queue bounds, reads all
DWORDs and validates the cursor before acknowledging. Each readiness check is
bounded; a hardware caller must apply an OS deadline when retrying a busy queue.

The single-packet FSP response parser validates the transport/vendor headers,
response type and requested command, and preserves firmware error codes. An
empty channel is never a success acknowledgement. Register traces verify these
rules on the CPU only. No native hardware transport implementation has acquired
the card or sent this request; GSP boot and physical rendering remain unproved.

AMD-Vi discovery and native v1 DMA page tables now target the host's Ryzen 7
5700X / ASRock B550M Pro4. ACPI discovery reads the full root table so IVRS is
not missed after MADT/FADT. IVRS checksums, record bounds, supported IVHD
formats and select/range/alias routing are validated. Unknown routing and
firmware-owned active controllers are refused. Normal discovery only reads
the controller; it never changes host Windows hardware.

Read-only Windows capture of the actual 208-byte IVRS also passes this parser.
Its legacy/extended definitions both route the host RTX 5060 at `06:00.0`
directly through unit `00:00.2`, MMIO `0xfd500000`, capability `0x40`.
This is evidence for firmware topology, not a NexusOS boot or MMIO test on
the physical machine. Reproduce it with `capture-ivrs.py` and `inspect_ivrs`.

The prepared RM/microcode/radix/signature frames also get an unpublished
read-only AMD-Vi domain. Every stored mapping is walked and checked for the
correct physical page and refused write access. Controller activation remains
exclusive to `amdvi-dma-test` until GPU reset, ownership and boot are ready.

`scripts/test-amdvi.ps1` uses QEMU's explicit EDU DMA test device and an AMD
IOMMU with DMA remapping enabled. It verifies >4 GiB nonidentity read/write
DMA with all 4096 bytes compared against freshly changed CPU memory; unmapped
and read-only device writes are refused with I/O page fault records and
unchanged buffers. Recovery, command-ring wrap, completion stores, controller
stop and exact frame reclamation pass. Endpoint data and tables are quarantined
if a stop cannot be confirmed. The disk is attached through a temporary
snapshot; the normal kernel is restored after the test.

The pinned QEMU build (`54e84cdc7a`) emits zero addresses in its AMD fault
records. The test checks the fault opcode/requester and unchanged destination;
accurate fault-address reporting on physical AMD hardware remains unverified.
EDU and QEMU DMA evidence is not RTX execution or physical hardware acceptance.

The kernel compiles and the QEMU boot verifies the absent-device path. Register
reads on the physical card have not been tested: Windows currently owns it.
Native hardware rendering is **not implemented**. Firmware framebuffer scanout
remains available without claiming that it is GPU command submission.

## Build and verification

```powershell
./scripts/build.ps1 -WithRtxFirmware -SkipDiskImage
./scripts/test-rtx-bootstrap.ps1
./scripts/build-rtx-image.ps1
./scripts/test-rtx-image.ps1
# Full GSP preparation (Python 3.14; first package download about 505 MiB):
./scripts/build.ps1 -WithGspFirmware -SkipDiskImage
./scripts/test-rtx-bootstrap.ps1 -WithGspFirmware
./scripts/build-rtx-image.ps1 -WithGspFirmware
./scripts/test-rtx-image.ps1 -WithGspFirmware
python tools/nexus-runtime/test_gsp_fetch.py
# LLVM clang compiler required; reads the original pinned C headers:
python tools/nexus-runtime/check-gsp-abi.py
./scripts/test-amdvi.ps1
# Optional read-only host topology check:
python tools/nexus-runtime/capture-ivrs.py
cargo run --offline -p nexus-nvidia --example inspect_ivrs -- build/amdvi-host-ivrs.bin 0600
```

The source fetch is pinned by SHA256. `prepare-nvidia.py` adapts the official
extractor to R615's aligned NvU64 bindata arrays and preserves the production
files and MIT notice. The basic bundle includes a bootloader and FMC;
`-WithGspFirmware` also includes the matching RM and external microcode.
Ordinary builds do not download firmware unless an explicit firmware option
is supplied. Matching runtime transport remains missing.

Host parser checks cover truncation, invalid spans/versions, section overlap,
bad checksums, non-firmware ELF and CRC-repaired files from a different release.
The real production bundle also passes the host inspector. The focused native
test reads it from a disposable disk, checks every copied byte and padding,
reclamation and allocation rollback, then boots a modified image and verifies
that the kernel refuses it. A second test boots the real UEFI image through
xHCI USB without virtio storage and reads the same material via the native
USB/FAT32 path. With the GSP option it also checks real RM/microcode bytes,
scatter pages, independent radix walks and rollback, then rejects a modified
RM file without leaking frames. It also checks the native boot buffers, untouched
remote queue, seven logs, mapping rights and allocation refusal during log setup.
The C ABI compiler probe compares 74 sizes/offsets/constants against NVIDIA's
headers using LLVM IR without executing generated code. Host tests cover packed
COT padding, authentication ownership, queue/region conventions and invalid
buffers, plus FSP transfer order, cursor/data failure, busy queues, malformed
responses and nonzero remote error codes. The archive tests refuse duplicate/symlink
members, missing firmware, malformed preambles and corrupted cached packages.
These are QEMU boot/storage/memory tests, not RTX execution.

During this verification, one normal QEMU boot stopped at the pre-existing IPC
self-test (`build/gsp-boot-arguments-normal-first-serial.log`). The same normal
kernel subsequently reached the desktop and its monitor report in both a
sequential run and a run concurrent with the USB test. The intermittent IPC
stop has not been diagnosed or claimed fixed by this GPU preparation change.

`build/rtx-5060-diagnostic.img` is a bootable diagnostic UEFI image (128 MiB
for bootstrap only, 256 MiB with full GSP material);
its SHA256 is beside it. It contains the Nexus kernel, pinned bootstrap files
and license notice. Generation does not write a physical disk or change
Windows. Its purpose on a real machine is to inspect PCI identity and bootstrap
preparation in the boot log. It is not a complete installation image or a GPU
accelerated desktop. Hardware acceptance remains pending.

## Official sources

Run `python tools/nexus-runtime/fetch-nvidia.py` to prepare the pinned NVIDIA
open kernel module source under `build/nvidia`. The revision and SHA256 are
recorded in the script. Register definitions come from
[NVIDIA's published reference header](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/ca2d03e6fafd4d4b56b383497d931c25b283bfcf/src/common/inc/swref/published/nv_ref.h).
The [official supported-device list](https://github.com/NVIDIA/open-gpu-kernel-modules)
identifies `2d05` as RTX 5060. The source is reference material for a native port;
fetching it does not make Linux kernel modules executable in NexusOS.

The full package pin comes from [NVIDIA's release checksum](https://us.download.nvidia.com/XFree86/Linux-x86_64/615.78.08/NVIDIA-Linux-x86_64-615.78.08.run.sha256sum).
The native radix format follows the pinned [resource manager implementation](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/ca2d03e6fafd4d4b56b383497d931c25b283bfcf/src/nvidia/src/kernel/gpu/gsp/kernel_gsp.c).
AMD-Vi protocol references are AMD publication 48882 and the tested
[QEMU implementation](https://github.com/qemu/qemu/blob/54e84cdc7a/hw/i386/amd_iommu.c).
The [EDU device specification](https://www.qemu.org/docs/master/specs/edu.html)
defines the independent DMA test endpoint. No Linux IOMMU driver source is
compiled into or copied as a driver implementation in NexusOS.

[NVIDIA's firmware extractor](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/ca2d03e6fafd4d4b56b383497d931c25b283bfcf/nouveau/extract-firmware-nouveau.py)
groups GB206 with GB202 and requires GSP for Blackwell. A port of NVIDIA's
resource manager requires firmware and userspace components matching its
release. A Nouveau/NVK implementation requires Nouveau's DRM and GSP interfaces;
the two kernel/userspace ABIs cannot be combined interchangeably.

## Remaining acceptance work

1. Native PCI resource ownership, interrupt routing and device DMA/IOMMU mapping.
2. Signed GSP firmware boot, authenticated microcode and host RPC transport.
3. VRAM allocations, GPU virtual address spaces, channels and completion fences.
4. A coherent userspace driver ABI and a real Vulkan ICD for the card.
5. GPU render and presentation tests on physical hardware, including recovery
   from failed submissions and window resize.
6. Steam's actual 32-bit runtime, network/process services and desktop integration,
   followed by browser download, installation, genuine sign-in and restart.

The real SwiftShader CPU Vulkan and Mesa software OpenGL probes are useful
runtime checks. They do not close any physical GPU acceptance gate.
System V semaphores and eventfd notifications now also pass real musl and
x86-64/i386 GNU libc tests. The actual Steam bootstrap proceeds past its
synchronization/post-FD initialization, but still exits during startup on
missing named FIFO and update-UI IPC services. Executable/proc metadata
now resolves the actual image, and real cwd/relative paths pass both libc widths.
Steam's chdir and data-link errors are resolved. Persistent links and the
native /dev/urandom descriptor pass actual libc tests; file locking,
permissions and i386 signals remain incomplete.
The decoded bootstrap diagnostic now explicitly identifies a refused fork
request while constructing the update UI. Native private address-space copying
passes, but child creation, descriptor inheritance and reaping are not wired:
see [native fork work](fork.md).
No Steam sign-in or physical
RTX submission has been verified.
