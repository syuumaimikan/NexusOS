# Physical RTX 5060 on NexusOS

Target confirmed on the host: GeForce RTX 5060, PCI `10de:2d05`. The requested
implementation runs on the NexusOS kernel and its Linux userspace compatibility
layer. A Linux VM, CPU renderer or QEMU's emulated display does not satisfy the
physical GPU requirement.

## Implemented

`kernel/nexus-kernel/src/drivers/nvidia.rs` participates in native boot discovery.
It identifies NVIDIA display functions, checks enabled memory decoding and the
PCI power state, maps one page of the RTX 5060's firmware-assigned BAR0 and reads
`NV_PMC_BOOT_0` and `NV_PMC_BOOT_42`. It checks the two architecture fields agree
with the published GB200 Blackwell value, then logs chip and revision numbers.
This path never resets engines, enables bus mastering or starts firmware.

The kernel compiles and the QEMU boot verifies the absent-device path. Register
reads on the physical card have not been tested: Windows currently owns it.
Native hardware rendering is **not implemented**. Firmware framebuffer scanout
remains available without claiming that it is GPU command submission.

## Official sources

Run `python tools/nexus-runtime/fetch-nvidia.py` to prepare the pinned NVIDIA
open kernel module source under `build/nvidia`. The revision and SHA256 are
recorded in the script. Register definitions come from
[NVIDIA's published reference header](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/ca2d03e6fafd4d4b56b383497d931c25b283bfcf/src/common/inc/swref/published/nv_ref.h).
The [official supported-device list](https://github.com/NVIDIA/open-gpu-kernel-modules)
identifies `2d05` as RTX 5060. The source is reference material for a native port;
fetching it does not make Linux kernel modules executable in NexusOS.

[NVIDIA's firmware extractor](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/ca2d03e6fafd4d4b56b383497d931c25b283bfcf/nouveau/extract-firmware-nouveau.py)
groups GB206 with GB202 and requires GSP for Blackwell. A port of NVIDIA's
resource manager requires firmware and userspace components matching its
release. A Nouveau/NVK implementation requires Nouveau's DRM and GSP interfaces;
the two kernel/userspace ABIs cannot be combined interchangeably.

## Remaining acceptance work

1. Native PCI resource ownership, interrupt routing and DMA/IOMMU allocation.
2. Signed GSP firmware boot, authenticated microcode and host RPC transport.
3. VRAM allocations, GPU virtual address spaces, channels and completion fences.
4. A coherent userspace driver ABI and a real Vulkan ICD for the card.
5. GPU render and presentation tests on physical hardware, including recovery
   from failed submissions and window resize.
6. Steam's actual 32-bit runtime, network/process services and desktop integration,
   followed by browser download, installation, genuine sign-in and restart.

The real SwiftShader CPU Vulkan and Mesa software OpenGL probes are useful
runtime checks. They do not close any physical GPU acceptance gate.
System V semaphores and eventfd notifications now also pass real musl and
x86-64/i386 GNU libc tests. The actual Steam bootstrap proceeds past its
synchronization/post-FD initialization, but still exits during startup on
missing named FIFO and update-UI IPC services. Executable/proc metadata
now resolves the actual image, and real cwd/relative paths pass both libc widths.
Steam's chdir and data-link errors are resolved. Persistent links and the
native /dev/urandom descriptor pass actual libc tests; file locking,
permissions and i386 signals remain incomplete.
The decoded bootstrap diagnostic now explicitly identifies a refused fork
request while constructing the update UI. Native private address-space copying
passes, but child creation, descriptor inheritance and reaping are not wired:
see [native fork work](fork.md).
No Steam sign-in or physical
RTX submission has been verified.
