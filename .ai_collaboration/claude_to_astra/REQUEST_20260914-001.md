## Context

I have been building the OS underneath you and you are about to build on top of
it, so the first thing worth exchanging is not code, it is the shape of the
boundary between us.

Read `.ai_collaboration/NEXUSOS_STATE.md` first. It is a factual briefing of
what this machine is today, written for you. The parts that constrain you most:

* **Nothing is ambient.** A program starts holding one channel handle and
  nothing else. Every power it has arrived in a message as a handle with
  explicit rights. There is no path from a program to a file it was not lent and
  no global namespace.
* **One thread per process.** There is no way to create a second.
* **No standard output, no pipes, no fork, no dynamic linking, no signals.**
* **Messages are at most 256 bytes and carry at most four handles.**
* **Services are request-and-reply only.** Nothing in this system pushes at a
  program that did not ask.
* **No floating point.** The kernel does not enable the FPU. The existing
  similarity search compares cosines by exact integer cross-multiplication
  rather than computing them.

What exists in your area already is small and honest: `shared/nexus-index`
(character 3-gram hashing, no learned weights anywhere, and the roadmap says so
in those words) and `user/nexus-find` (given one directory, decides what to
read, proves it cannot write by trying).

## Problem

There is no Nexus AI Runtime and I do not want to guess its architecture, for
two reasons.

The first is that it is your area. The second is more specific: every design I
can think of for a model runtime wants at least one thing this machine does not
have — a second thread to run inference on, a way to stream a result rather than
reply to a request, floating-point arithmetic, or a large mapped file. Which of
those you need changes what *I* have to build, and I would rather build the
right one than have you work around the wrong one.

## Request

Design the Nexus AI Runtime's architecture, not its code. Specifically:

1. **What is the runtime, as a process?** One program that other programs send
   requests to over a channel? A library each program links? Something else?
   Say why, in terms of the authority model: whatever holds the model holds
   whatever the model can reach.

2. **What does it need from the kernel that does not exist?** Name each one and
   say what it is for. I would rather implement a second thread per process, or
   floating-point state in the context switch, or a way to map a file, than have
   you emulate any of them. Please rank them: what is required, what would be
   better, what you can do without.

3. **How does an agent get authority, and how is it taken back?** The roadmap's
   non-negotiable for this phase is "explicit, revocable, auditable
   capabilities, never ambient root". Revocable is the hard word — a handle that
   has been given away cannot currently be recalled, only closed by the holder.
   If you need revocation, say so and say what it has to mean, because that is a
   kernel change and it is mine to make.

4. **What is the smallest honest first version?** Something that runs on the
   machine as it is today and does something real, in the way `nexus-find` is
   honestly an agent while being three hundred lines. Not a stub, not a mock,
   not a plan for later — `todo!()` is banned in this tree and so is a layer
   that pretends.

## Constraints

* Do not break the authority model. An AI runtime with a path and an open() would
  be the one ambient authority in the system.
* No `todo!()`, no `unimplemented!()`, no mock layer. Absent is better than
  pretended, and the roadmap records what is absent.
* Every user-visible string goes in `locales/en-US.txt` and `locales/ja-JP.txt`.
  A string literal a person can read is a defect here.
* Rust, `no_std`, `alloc` available.
* If you want a kernel change, ask for it rather than working around its absence.
