## Changes

Every window on this machine was doing the same four things itself — take a
surface from the compositor, map it, draw a frame and say so, wait to be told
what happened — and five programs each had their own copy of that hundred-and-
twenty-line handshake. A handshake copied five times is a handshake that is
subtly different in one of them.

`user/nexus-window` is that handshake, once. A program implements `App` and
calls `Window::open` then `window.run`. It deliberately does not live in
`nexus-ui`, which says of itself that it knows nothing about windows or input
and should go on not knowing.

Two windows are written against it: the settings window (one row per settings
key, each of which something actually reads) and the package window (a list of
what is in `PKG/`, with Enter bound to the same `install` the updater calls).

The five existing windows are untouched. They work, and rewriting five working
programs to prove a library is the wrong order to do it in.

## Questions

You will be building AI UI on this, so the API is as much yours as mine. Three
things I am unsure about:

1. **`ticked()` conflates two events.** A clock tick and a watched handle
   becoming ready both arrive as `ticked() -> bool`, because from the frame
   loop's point of view they are the same question: has anything changed? A
   program watching three services has to poll all three to find out which one
   it was. Should `ticked` carry the key that woke it — `fn woken(&mut self, key:
   Option<u64>) -> bool` — or is polling the right answer for a machine where a
   program has at most a handful of watched handles?

2. **There is no way for a program to say *which part* of its surface changed.**
   `damaged` is a bare message and the compositor repaints the whole window. For
   an AI UI streaming text into a pane this is a full-window repaint per token.
   I can add a rectangle to the message. Is a single bounding box enough for what
   you intend to draw, or do you need a list?

3. **`run` takes `self` and ends when the compositor stops answering.** A program
   that wants to do work between frames has to do it inside `draw` or `ticked`,
   because there is no second thread. If the AI runtime blocks on a reply, the
   window stops drawing. Does that force the runtime to be a separate process,
   or do you want a non-blocking `pump()` shape instead of `run()`?
